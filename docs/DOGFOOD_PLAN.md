# 실제 업무 시험 계획 (사전 등록 — 결과를 보기 전에 정함)

목적: DevOrch 를 **실제 업무 작업**에 쓰면서 ① 비용이 얼마나 드는지, ② 비용 절감 주장이 성립하는지, ③ 어디서 막히는지를 기록한다.
기간/규모: 실제 작업 약 10건(2주 안팎). 건수가 적어 **통계가 아니라 방향을 가늠하는 용도**다.

## 무엇을 재고, 무엇을 못 재는가 (먼저 못 재는 것)
- `devorch usage` 는 **DevOrch 가 부른 LLM(리뷰어) 비용만** 보여 준다. Claude Code 등 **에이전트 자신의 비용은 안 보인다.** → 에이전트 비용은 별도로(구독 사용량 화면/청구서) 적어야 한다.
- "비용 절감"은 **비교 기준이 있어야** 말할 수 있다. 기준 = "모든 작업에 리뷰어를 전부 붙였다면"의 추정 비용(`review_estimate`/`estimate_cost` 의 범위값). 이 기준은 **추정**이고 실제 청구가 아니다.
- 10건으로는 "일반적으로 절감된다"고 말할 수 없다. 이 프로젝트·이 작업 종류에서의 관찰일 뿐이다.

## 작업마다 기록 (표 한 줄)
| 항목 | 출처 |
|---|---|
| 날짜 / 작업 한 줄 | 직접 |
| DevOrch 위험도(LOW/MEDIUM/HIGH/CRITICAL)와 붙은 리뷰어 수 | `analyze_task` 응답 / `devorch tasks` |
| **실제 DevOrch 비용**($, 단가 없는 호출은 '알 수 없음' 그대로) | `devorch usage --days 14` |
| **리뷰어를 전부 붙였다면의 추정 비용**(범위) | 응답의 `review_estimate` (이미 붙인 만큼 빼고 차이만 '아낀 추정') |
| 승인이 필요했나 / 승인까지 걸린 시간 | 직접 |
| 막히거나 번거로웠던 곳 (한 줄) | 직접 |
| DevOrch 가 **틀렸다**고 느낀 곳 (위험도를 너무 낮게/높게 분류, 놓친 문제, 오탐) | 직접 — 가장 중요 |
| 에이전트(Claude Code) 쪽 사용량 | 구독 사용량 화면 (참고용, DevOrch 와 분리) |

## 준비 (비용이 드는 부분 — 시작 전 동의)
- 실제 리뷰어를 쓰려면 API 키가 필요하다. **키는 환경변수로만** 넣고 파일·채팅에 쓰지 않는다. `--mock` 이면 비용 0이지만 리뷰가 가짜라 비용 측정이 의미 없다.
- 시작 전에 `devorch usage` 의 단가 설정(`config.yaml` 의 가격표)이 채워져 있는지 확인한다. 단가가 없으면 비용이 '알 수 없음'으로 나온다.
- 작업당 상한 `limits.max_cost_usd` 를 작게(예: 0.5) 걸어 둔다 — 지금 기본은 무제한이다. 이 상한은 **쓰는 모든 provider 의 단가가 있어야** 동작한다(단가는 추측하지 않으므로 공급사 가격 페이지를 보고 직접 적는다).
- 대상 프로젝트는 실제 업무 저장소 **복사본이 아니라 본체**여도 되지만, 첫 1~2건은 중요도 낮은 작업으로 시작한다.

## 끝난 뒤 판단 기준 (미리 정함, 결과를 보고 바꾸지 않기)
- **계속 쓸 가치**: 10건 중 (a) 막혀서 포기한 작업이 2건 이하이고 (b) DevOrch 가 위험도를 심하게 틀린 사례(위험한 변경을 LOW 로 분류 등)가 없다.
- **절감 주장 가능**: 리뷰어를 줄인 작업이 있었고, 그 '아낀 추정'이 같은 기간 DevOrch 실제 비용보다 크다 — 단 **추정**이라고 표시하고, 놓친 문제가 없었는지 함께 본다(아껴서 놓쳤다면 절감이 아니다).
- **고칠 것 목록**: '틀렸다고 느낀 곳'과 '막힌 곳'을 모아 우선순위를 정한다. 숫자가 아니라 사례 기준.
- 위험도 분류가 틀린 사례가 나오면 그 **입력과 분류 결과를 그대로** 기록한다. 결과를 본 뒤 매처를 맞춰 고치지 않는다(별도 검증 없이 튜닝 금지).
