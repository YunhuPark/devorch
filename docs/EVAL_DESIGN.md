# 실제 코드 평가 세트 설계 (사전 등록 — 결과를 보기 전에 고정)

상태: **설계안, 아직 아무것도 실행하지 않음** (2026-10-13). 이 문서가 고정되기 전에는 평가를 돌리지 않는다. 고정 뒤에는 방법을 바꾸지 않고, 바꿀 때는 이유와 날짜를 아래 "변경 기록"에 남긴다.

## 1. 왜 하는가
DevOrch를 "AI가 한 변경이 그대로 반영되는 사고를 막는 통제 도구"로 내세우려면 두 가지가 필요하다.
- 통제 장치(승인 게이트, 테스트 강제, 시크릿 차단, 비용 상한, 감사 로그): 결정적 규칙이라 **이미 테스트로 확인됨**.
- **AI 리뷰어가 실제 코드의 버그를 얼마나 찾고 얼마나 헛경보를 내는가: 확인된 적 없음.** 지금까지는 우리가 일부러 심은 결함 16케이스뿐이고, 다중 리뷰와 단일 리뷰의 탐지 차이는 통계적으로 확인되지 않았다(쌍체 p=0.5~1.0).

이 평가는 두 번째 항목만 답한다. 결과가 나쁘면(탐지가 낮거나 오탐이 많으면) 그대로 공개하고 포지셔닝을 "리뷰가 버그를 잡아 준다"가 아니라 "통제 장치"로 둔다.

## 2. 무엇을 재는가
1. **탐지율(결함 단위)**: 실제로 버그를 도입한 변경을 리뷰했을 때, 리뷰어가 그 버그를 *지적했는가*(차단 또는 경고).
2. **오탐(깨끗한 변경 단위)**: 이후 오래도록 문제가 없던 변경에 *차단(blocking)* 지적이 나오는 비율, 그리고 그 지적이 맞는지(사람이 판정).
3. **비용**: 구성별 diff당 실제 비용과 "찾은 버그 1건당 비용".
4. 구성 비교(같은 diff에 모두 적용). 이름은 `devorch bench` 실행 모드와 같다:
   - A = `multi`: 정책의 HIGH 전문 리뷰어 + 일반 리뷰어 = 보안(OpenAI) + 아키텍처(Gemini) + 일반 리뷰(OpenAI), **3명** (처음 문서에 2명으로 적은 것은 실제 코드와 달라 2026-10-14 정정)
   - B = `single`: 일반 리뷰어 1명(OpenAI)
   - C = `solo:gemini:review`: 일반 리뷰어 1명(Gemini)
   (구현 모델 Claude는 리뷰에 쓰지 않는다 — 구현과 리뷰의 독립성 원칙.)

## 3. 데이터
**3-1. 버그를 도입한 변경(양성)** — 목표 30건 이상
- 출처 ① (보조로 격하, 2026-10-14 실측 — 변경 기록 참조) **이 저장소의 자체 역사**: 나중에 고친 커밋이 있는 변경(예: 제안 diff를 CRLF로 저장한 변경, 비용 상한이 NaN에 뚫리던 변경). 모델이 학습했을 가능성이 거의 없다(오염 낮음). 단, 건수가 적고 작성자가 같다.
- 출처 ② (주 출처) 공개 저장소: 최근(예: 최근 6개월), 활발하고 테스트가 있는 Python 저장소에서 `bug` 라벨 이슈를 닫은 PR을 찾아, 그 버그를 도입한 커밋을 `git blame`/`git log -S`로 추적(SZZ 방식). 변경이 3개 파일 이하, diff 1~20 KB(비용 모델이 검증된 범위; 4만 토큰 초과는 제외).
- **라벨 확인(필수)**: 도입 커밋 시점에서 수정 PR의 테스트를 돌려 실패하고, 수정 후 통과하는지 확인할 수 있는 것만 채택. 확인 못 한 것은 제외하고 제외 수를 보고.
- 한계로 명시: 오염(공개 저장소 버그는 모델이 봤을 수 있음), 추적 오류(도입 커밋이 아닐 수 있음), 한 언어(Python)만.

**3-2. 깨끗한 변경(음성)** — 양성과 같은 수
- 같은 저장소·같은 기간의 커밋 중, 이후 12개월(또는 가능한 만큼) 동안 어떤 수정 커밋에도 걸리지 않고 되돌려지지도 않은 것. 크기 분포를 양성과 맞춘다.
- 한계: "알려진 버그 없음"이지 "버그 없음"이 아니다. 그래서 오탐은 사람이 개별 판정한다.

## 4. 실행
- 기존 `devorch bench` 재사용: 케이스 형식(before/after 파일 + defects)에 커밋을 변환하는 임포터를 추가한다(`before`=부모 커밋 파일, `after`=해당 커밋 파일). 실제 버그는 정규식으로 매칭할 수 없으므로 **LLM 판정기(`bench judge`) 기반 채점**을 쓴다(판정기는 구성 정보를 보지 못하는 블라인드, 프롬프트 고정, 파싱 실패는 "미판정"). 판정기가 구현·리뷰와 같은 회사 모델이면 편향 가능성을 기록한다.
- 반복 2회, **단위는 결함(독립 표본)** — 같은 diff의 반복은 표본 수를 늘리지 않는다(원칙 10). 과반수로 결함 단위 탐지를 정한다.
- 비용 상한: `--max-total-usd` 로 고정. 사전 추정: 120 diff × (A≈$0.04 + B≈$0.013 + C≈$0.015) × 반복 2 ≈ **$17 (범위 $9~$30 추정)** — 단가·토큰은 이번 리뷰 관측 기반 추정이며 작은 diff에서도 Gemini 출력이 크게 튀는 것이 확인됐으므로 상한 $30으로 시작해 중간 점검한다.

## 5. 분석과 판정 규칙 (미리 정함)
- 1차: 구성별 결함 단위 탐지율 + 95% 신뢰구간(부트스트랩), A 대 B 쌍체 비교(맥니마/부호 검정).
- 오탐: 깨끗한 diff당 차단 지적 수, 그중 사람이 "맞는 지적(개선할 점)"으로 판정한 비율을 따로 보고. 헛경보와 맞는 지적을 섞지 않는다.
- 판정 기준(결과 보기 전에 고정):
  - A가 B보다 탐지율이 높고 차이의 신뢰구간이 0을 제외하면 "다중 리뷰가 더 잡는다"고 쓴다. **그렇지 않으면** "다중 리뷰의 추가 탐지는 확인되지 않았다"고 쓰고 HIGH 기본값(리뷰어 3명) 재검토 근거로 쓴다(CRITICAL의 독립 리뷰어 2명은 통제 규칙이므로 이 결과만으로 바꾸지 않는다).
  - 탐지율이 낮으면(예: 절반 미만) 문구에서 "버그를 잡아 준다" 계열 표현을 쓰지 않는다.
- **검정력의 한계**: 양성 30건이면 큰 차이(대략 +25%p 이상)만 구분할 수 있다. 작은 차이는 "확인되지 않음"으로 남고 이것이 "차이 없음"의 증거는 아니다. 결과는 탐색적 수준으로 표기한다.
- 채점기·매칭 규칙은 결과를 본 뒤에 고치지 않는다. 관측된 한계는 케이스 노트에 기록(사전 등록 원칙).

## 6. 하지 않는 것 / 알려진 위험
- 모든 언어·프레임워크를 대표하지 않는다(Python, 작은 diff 한정).
- 리뷰어의 *프롬프트 개선*으로 점수를 올리는 작업은 이 평가 *이후*에 하고, 개선 전후를 새 hold-out 표본으로 다시 잰다.
- 정답 라벨의 오류(도입 커밋 오추적)는 일정 비율 존재한다. 확인 방법과 제외 수를 보고서에 적는다.
- 공개 저장소 코드를 외부 LLM API에 보낸다(공개된 코드이며 비밀이 없는 것만; 자격증명 형태 문자열이 있으면 DevOrch가 호출 전에 거부).

## 7. 사람이 해야 하는 일 (시간 추정)
- 양성 후보 확인과 오탐 지적 판정: 건당 약 10~15분 × 60~90건 ≈ 10~20시간(추정). 기계적 작업(후보 수집, 변환, 실행, 집계)은 코드로 하고, **정답 라벨과 지적의 옳고 그름은 사람이 최종 확인**한다.
- 결정 필요: ① 언어 범위(Python만?) ② 비용 상한 ③ 라벨 확인에 쓸 수 있는 시간 ④ 공개 저장소 diff를 외부 API로 보내도 되는지.
