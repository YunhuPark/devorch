# DevOrch 사례 연구 — AI 에이전트가 낸 코드를 "승인 없이는 반영되지 않게" 통제하는 도구

> 이 문서의 모든 수치는 저장소의 기록(`HANDOFF.md`, `docs/DOGFOOD_LOG.md`, `docs/EVAL_DESIGN.md`, CI 결과, git 이력)에서 가져왔고, 표본 크기와 한계를 함께 적었다. **측정하지 않은 것은 "미측정"이라고 쓴다.**

## 한 줄 요약
AI 코딩 에이전트(Claude Code 등)가 만든 변경을 **위험도 분석 → 독립 리뷰 → 테스트 → 사람 승인 → 별도 브랜치 커밋 → 서명된 감사 기록**으로 통제하는 MCP 서버/CLI. 기능을 만드는 것보다 **"안 되어야 하는 경로"를 실제로 깨 보고(재현), 고치고, 일부러 안전장치를 망가뜨려 테스트가 잡는지 확인**하는 방식으로 만들었다.

## 안전장치를 실제로 깨 본 기록
| 시도(에이전트 입장) | 결과 |
|---|---|
| 승인 파일 한 개를 직접 써서 `approval_required` → `committed` | **가능했음(재현, 2026-10-14)** → 승인·작업 기록을 서명, 서명 키는 프로젝트 밖 |
| 악의적 테스트가 키를 읽어 스스로 승인 | **샌드박스 없이는 가능(재현, 2026-10-15)**, **Docker 샌드박스에서는 막힘(실제 Docker 로 확인)** |
| 정책·설정 파일 변조(`protected_paths` 삭제, `test_command` 교체) | **가능했음(재현, 2026-10-20)** → 정책 승인 기록으로 차단 |
| 감사 로그 중간 수정·삭제·순서 변경·끝부분 잘라 내기 | `devorch audit` 가 찾아냄(막는 것은 아님) |
| 리뷰·테스트 뒤에 diff 를 바꿔 커밋 | 게이트가 diff 의 SHA 에 묶여 있어 무효 |

안전장치마다 **일부러 망가뜨려 테스트가 잡는지** 확인했다. 최근 기능 5개에서만 33종을 확인했고, 처음엔 못 잡은 것이 있어 테스트의 단언을 고친 경우가 3번 있었다(변형 시험이 드러낸 2번, 검토에서 발견한 1번 — 기록에 남김).

## 모델에 기대지 않고 코드로 잡는 신호 — 약해진 테스트 감지
에이전트가 테스트를 지우거나 건너뛰게 하거나 `assert True` 로 바꾸면 테스트 단계가 "통과"한다. diff 의 *줄*을 읽어 이걸 잡는다(비용 0, 모델 없음, 올리기만, 끌 수 있음). 규칙을 **측정 전에 고정**하고 실제 이력에 적용했다.
- 테스트 44개, 변형 시험 10종 모두 잡음(실패하는 테스트를 지우면 MEDIUM+리뷰어, 삭제+skip 이면 HIGH+승인).
- **실제 이력 129개 커밋(2개 저장소)에서 5건이 걸렸고, 내가 읽고 판정한 결과 1건만 정당한 지적**(정밀도 1/5 — 표본이 매우 작음). 오탐은 조건부 skip 3건과 `pytest.raises` 로 바꾼 리팩터 1건.
- **재현율은 실제 이력으로 측정하지 못했다**(라벨된 양성이 없음). 합성 사례로만 확인. 결과를 보고 규칙을 고치지 않고, 개선안은 v2 후보로 기록(`docs/DOGFOOD_LOG.md`).

## AI 리뷰어는 버그를 얼마나 찾나 — 측정 결과 (정직하게)
실제 공개 저장소(glances, poetry)에서 **나중에 고쳐진 진짜 결함 12개**를 케이스로 만들어 리뷰어 구성을 비교했다(판정 기준은 실행 전에 확정, 결과를 보고 고치지 않음).

| 구성 | 탐지 | 95% 구간 |
|---|---|---|
| multi(리뷰어 3명) | 5/12 = **42%** | 19~68% |
| single(1명) | 3/12 = 25% | 9~53% |
| Gemini 단독 | 2/12 = 17% | 5~45% |

- **구성 간 차이는 통계적으로 유의하지 않았다**(쌍체 검정 p=0.25~0.5). "multi 가 더 낫다"고 말할 수 없다.
- **어떤 구성도 못 잡은 결함이 7/12**, 그중 4개는 세 구성 모두 지적 0건(리뷰는 `READY` 를 냄). 잡힌 것은 diff 안에 국소적 흔적이 있는 결함이었다.
- 그래서 이 도구는 "버그를 잡아 주는 도구"가 아니라 **"승인 없이는 반영되지 않게 통제하는 도구"** 이고, `READY` 는 안전 보증이 아니라고 응답마다 적는다.
- 비용: 이 평가에 실제로 쓴 돈은 리뷰어 $1.42 + 판정 $0.13 = **$1.55**(사전 추정 $1.17의 1.3배 — 추정이 낮았다). 전체 실제 LLM 지출은 약 $2.73.
- 한계: 결함 12개·저장소 2곳·반복 2회, 결함 설명은 내가 썼고 판정기와 같은 계열 모델이라 편향 가능, 대조군은 '알려진 버그 없음'일 뿐.

## 한계와 하지 않은 것 (숨기지 않음)
- **미측정:** 실제 리뷰어를 붙인 작업의 비용·절감. (프로젝트의 원래 동기는 회사 AI 비용이었지만, 절감은 아직 **증명하지 못했다.**)
- **위험도 분류는 경로만 본다.** 내용 기반 신호가 없어 소유자가 보호 경로를 지정해야 한다.
- **Docker 샌드박스 없이는 악의적인 에이전트를 못 막는다.** 에이전트 *자신의* 셸이 서명 키를 읽는 경로는 DevOrch 가 막을 수 없다(호스트 설정이 필요, 미검증).
- 사람이 내용을 보지 않고 승인하면 소용없다(위험한 변경은 `accept` 를 직접 입력하게 해 완화만 함).
- 다른 사용자/팀의 수요는 **검증하지 않았다**(인터뷰 안 함). 실사용은 내 저장소 1개 + IDE 실사용 3회.
- Linux/macOS 는 테스트·깨끗한 설치 수준에서만 확인(실제 `run --apply`·MCP 사용은 미검증), npm/mvn/gradle 은 실제 저장소로 미검증.

## 개발 방식
Claude Code 와 함께 개발했다. 사람이 정한 원칙: 측정 전에 판정 기준 확정, 결과를 보고 규칙을 맞춰 고치지 않기, 안전장치는 일부러 깨 보기, 확인하지 못한 것은 "미검증"으로 쓰기, 키는 환경변수로만. 상세 기록: `HANDOFF.md`(원칙·상태), `docs/DOGFOOD_LOG.md`(실사용 시험), `docs/EVAL_DESIGN.md`(평가 설계·결과).
