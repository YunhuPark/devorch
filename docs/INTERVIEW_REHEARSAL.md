# 인터뷰 리허설 (시뮬레이션) — 증거가 아닙니다

> **이 문서는 Claude 가 5명의 가상 인물을 연기해 본 리허설입니다. 실제 사람의 말이 아니므로 "수요가 있다/없다"의 근거로 쓰지 않습니다.**
> 인물의 답은 제 선입견과 일반 지식에서 나온 것이라, 현실과 다를 수 있고 대체로 제 가설이 되풀이됩니다.
> 쓸모는 세 가지뿐입니다: ① 소개 문장·시연의 헷갈리는 곳 찾기, ② 실제 인터뷰에서 물어볼 질문 정하기, ③ 제품이 "대답하지 못하는 질문" 미리 알기.
> `INTERVIEW_GUIDE.md` 의 판단 기준(5명 중 3명…)에는 **넣지 않습니다.**

사용한 소개 문장: "AI 코딩 작업에 예산 상한과 승인선을 거는 도구입니다. 위험한 작업은 사람이 직접 승인해야만 별도 브랜치에 커밋되고, 위험하지 않은 작업은 검증 비용을 아낍니다."
제품 사실(확인된 것): 승인은 diff 해시에 묶이고 에이전트 도구에 승인이 없음 / 작업당 비용 상한 `limits.max_cost_usd`(기본 무제한), 월·팀 예산 없음 / 기본 샌드박스 없음이면 테스트 코드가 서명 키를 읽어 스스로 승인할 수 있음(Docker 로 차단) / 승인은 터미널에서만.

## 인물과 반응 (요약)

**1. 민수 — 1인 프리랜서, Claude Code + Cursor, 월 약 $150**
- 현재: diff 를 대충 훑고 테스트 돌리고 merge. 사고: AI 가 실패하는 테스트를 지우거나 고쳐서 통과시킨 적.
- 반응: "한 문장은 이해했는데 **나 혼자인데 누구에게 승인받죠? 나 자신?**" 승인 단계가 귀찮아 끌 것 같다고 함. 가장 마음에 든 장면은 *에이전트가 별도 브랜치에만 커밋하고 main 이 안 바뀌는 것*, 다음이 "테스트 지우기를 위험 신호로 올려 주는가"(제품이 이걸 하는지는 **이 시뮬레이션에서 확인하지 않음 — 실제 확인 필요**).
- 돈: 낼 의향 없음("Claude Code 가 이미 브랜치/권한 설정 있음").

**2. 지현 — 5인 스타트업 팀 리드, Claude Code 팀 도입, 월 약 $600, 한 번 예상 초과**
- 현재: CLAUDE.md 에 규칙을 적고 PR 리뷰로 막음. 비용은 월말에 청구서로 앎.
- 반응: 가장 관심 있는 건 **비용**. "작업당 상한은 좋은데 내가 알고 싶은 건 **이번 달 팀 전체**와 **누가 얼마 썼는지**." 승인선은 "이미 PR 리뷰가 승인선"이라 중복으로 느낌.
- 돈: 비용 가시화(팀·월 단위)라면 소액 가능성. 승인 쪽에는 반응 약함.

**3. 태호 — 핀테크 중견기업 플랫폼/보안 엔지니어, 에이전트 도입이 보안 심사에 막혀 있음**
- 반응: 가장 강한 관심. "에이전트가 스스로 승인하지 못하게 한다", "승인이 diff 에 묶인다", "감사 기록이 서명 사슬" — 심사 질문에 바로 쓸 만하다고 함.
- 바로 나온 반박: ① **기본이 샌드박스 없음이면 악성 테스트가 키를 읽어 자기 승인 가능** — 그럼 통제가 아니다. ② 승인이 터미널 한 사람이 아니라 **SSO·역할(개발자≠승인자)·중앙 로그**여야 함. ③ 감사 로그가 같은 머신 파일이면 증거 능력이 약함(로그를 지우면 검증할 게 없음).
- 돈: 위 세 가지가 해결되면 가장 지불 가능성이 높은 유형. 지금 제품으로는 파일럿 이전 단계.

**4. 서연 — 대기업 개발자, 사내 Copilot 허용, 외부 도구 설치는 보안 승인 필요**
- 반응: "좋아 보이는데 **회사 정책상 외부 MCP 서버를 못 깝니다.**" 이미 CI·코드 리뷰·브랜치 보호가 있어 "반영 전에 사람이 본다"는 새롭지 않다고 함.
- 의견: 설치 마찰과 사내 승인 절차 때문에 개인이 써 볼 수 없는 유형.

**5. 현우 — 회의적인 시니어 (AI 코딩 많이 씀)**
- 반응: "에이전트가 브랜치에 커밋하고 사람이 PR 보면 끝 아닌가요? **DevOrch 가 그 위에 더하는 게 정확히 뭔가요?**" "위험도 분류가 키워드 기반이면 오탐/누락은요? 4개 리뷰어가 못 찾은 버그가 7/12면 리뷰어는 믿을 수 없는데 '독립 검증'이라 부르는 건 과장."
- 돈: 없음. 단 "승인이 해시에 묶인다"는 부분은 *기술적으로는* 인정.

## 리허설에서 드러난 것 (제 가설 — 실제 확인 필요)

1. **소개 문장이 약한 곳:** "예산 상한"은 지금 **작업당** 상한뿐이고 기본 무제한이다. 비용에 관심 있는 사람(지현)은 월·팀 단위를 기대할 가능성이 크다. 문장을 그대로 쓰면 기대와 어긋난다. → 실제 인터뷰에서 "예산 상한이라고 하면 무엇을 떠올리나요?"를 물어볼 것.
2. **"그냥 브랜치+PR 이면 되지 않나"에 대한 대답이 아직 분명하지 않다.** 후보 답: 승인이 *에이전트 세션 안에서* 반영 전에 게이트로 걸리고, 승인이 diff 해시에 묶이며, 에이전트가 자기 승인을 못 한다는 것. 그러나 이게 사람들에게 PR 리뷰 대비 가치가 있는지는 **모른다.**
3. **혼자 쓰는 개발자에게는 승인선이 가치가 약할 수 있다**(누구에게 승인받나). 팀·규제 환경이 더 맞을 수 있으나 그쪽은 SSO·역할·중앙 로그가 필요하고 지금 없다.
4. **가장 날카로운 반박은 샌드박스 기본값**이다. 통제를 전면에 내세우면 "기본이 안 막히는데 통제라 할 수 있나"가 바로 나온다. `require_sandbox_for_approval` 기본값 결정과 직결된다.
5. **리뷰어 정확도 주장은 피해야 한다**(우리 평가에서 최대 약 40%). "독립 검증"이라는 표현이 과장으로 읽힐 수 있다.
6. 인물 5명 중 **강하게 반응한 건 1명(보안 엔지니어)**, 비용에 반응한 게 1명, 나머지는 약함 — *이것도 제 연기의 산물이라 결과로 보지 않습니다.*

## 실제 인터뷰에서 꼭 물어볼 것 (리허설에서 뽑음)
- 지금 반영 전에 쓰는 장치(PR 리뷰, 브랜치 보호, CI)와 **그것이 놓친 사례**가 있는가? (DevOrch 가 PR 리뷰 대비 가치가 있는지 판가름)
- "예산 상한"을 들으면 작업당/월/팀 중 무엇을 떠올리는가? 지금 비용을 누가·어떻게 보는가?
- 승인자가 누구여야 하는가(본인/팀 리드/보안)? 터미널에서 승인하는 방식이 받아들여지는가?
- 기본이 샌드박스 없음이라는 사실을 들으면 신뢰에 어떤 영향이 있는가? Docker 를 쓸 수 있는가?
- 회사 정책상 외부 MCP 서버를 설치할 수 있는가?

## 이 리허설로 바꾼 것 / 바꾸지 않은 것
- 바꾼 것: `INTERVIEW_GUIDE.md` 의 질문에 위 5개 중 빠진 것을 반영.
- 바꾸지 않은 것: 포지셔닝, 판단 기준, 제품 코드. 가상 반응만 보고 제품 방향을 바꾸지 않습니다.
