# 실제 업무 시험 기록 (`DOGFOOD_PLAN.md` 의 계획에 따름)

## 시험 1 — algo-pipeline (2026-10-17)

**대상:** 사용자의 저장소 `YunhuPark/algo-pipeline`(Python, 인스타그램 카드뉴스 자동 발행, 테스트 30파일). 선택 이유: 소유한 저장소, pytest 경로(DevOrch 에서 가장 검증된 경로), 인증·발행처럼 위험도가 갈릴 만한 코드가 있음, 테스트가 있어 기준선 확인 가능. 같은 조건으로 비교한 다른 후보는 golden-time(TS+npm — npm 경로는 실제 저장소로 검증된 적 없음), yt-growth-coach(비공개 TS), IMST-Mamba(torch 필요).
**방식:** 사용자의 작업 폴더가 아니라 **임시 폴더에 새로 복제**해서 진행(원격에는 아무것도 push 하지 않음). 이 시험은 **가짜 리뷰어(mock, 비용 $0)** 로 DevOrch 의 분류·테스트·커밋 흐름만 확인했다. 실제 에이전트가 아니라 내가 스크립트로 에이전트 역할을 했다(작업 1건, 사소한 변경).

### 된 것
- 기준선: 새 복제본에서 테스트 **200개 통과**(저장소 자체 CI 와 같은 환경: `ALGO_ENV=test`, 가짜 키, 임시 DB). 테스트가 `.db` 등 부작용 파일을 남기지 않음.
- 작업 "루트에 잘못 생성된 `=0.40.0` 파일 삭제": 분석(LOW, 리뷰어·승인 불필요) → 리뷰(READY) → DevOrch 의 임시 worktree 에서 테스트 **200개 통과** → 별도 브랜치 `devorch/494ac382-0-40-0` 에 커밋(`d562bf8`, 삭제 1건만, 메시지에 위험도·`Human-Approved: not required`) → `devorch finish` 로 작업 트리 정리 → `git merge` fast-forward 성공. 내용 줄이 없는 **빈 파일 삭제 diff 도 문제없이 처리**됨.
- 테스트가 실패하면(아래 발견 3) `apply_changes` 가 "통과한 테스트 없음"으로 **막혔다**(fail-closed 확인).

### 발견 (DevOrch 쪽 — 후보 개선, 아직 만들지 않음)
1. **테스트에 환경변수를 넘기는 공식 방법이 없다.** 이 저장소의 테스트는 `TAVILY_API_KEY` 에 값이 *아무거나* 있어야 시작하는데, DevOrch 는 이름에 key/token/secret 등이 든 환경변수를 테스트 실행에서 제거한다(안전 장치, 의도된 동작). 그래서 그대로는 **테스트가 시작도 못 한다.** 이번에는 저장소 밖에 실행 스크립트(`run_tests.py`)를 두어 CI 와 같은 가짜 값을 설정하는 방식으로 우회했다. 이런 저장소(테스트에 가짜 키 필요)는 흔할 것으로 **추정**한다. 후보: `project.test_env`(리터럴 가짜 값만, 실제 비밀처럼 보이는 값은 거부). **→ 2026-10-18 구현함**(`config.yaml` 의 `project.test_env`, 테스트 19개 + 보호 5종 변형 시험). 같은 저장소에서 우회 스크립트 없이 `test_env` + 평범한 `pytest` 명령만으로 DevOrch 가 테스트 200개를 통과시키고 커밋함(작업 `abf26397`). 일반성은 저장소 1개 근거라 **추정**.
2. **위험도 분류 의심 사례 1건(판정은 사용자):** "인스타그램 발행 로직에서 **승인 큐를 우회하는 버그** 수정" 이 **LOW**(리뷰어·승인 없음)로 나왔다. 자동 게시 시스템의 발행 승인 우회라면 더 높아야 한다고 볼 수 있다. 단 이 분류는 diff 가 생기기 전의 작업 *문장* 기준이고, diff 가 생긴 뒤에는 실제 변경으로 위험도를 올리는 재평가(raise-only)가 있다 — 이 시험에서는 diff 를 만들지 않아 **재평가가 이것을 올렸을지는 확인하지 못했다.** 매처를 이 결과에 맞춰 고치지 않는다.
   | 작업 문장(내가 쓴 것) | 위험도 | 리뷰어 |
   |---|---|---|
   | 루트에 잘못 생성된 '=0.40.0' 파일 삭제 | low | 없음 |
   | README 오타 수정 | low | 없음 |
   | 인스타그램 발행 로직에서 승인 큐를 우회하는 버그 수정 | **low** | 없음 |
   | 인스타그램 액세스 토큰 갱신 로직 수정 | medium | review, security |
   | 카드뉴스 폰트 크기 조정 | low | 없음 |
   | 매일 실행 스케줄러 시간을 오전 9시에서 8시로 변경 | low | 없음 |
   | run_daily.py 의 재시도 횟수를 3에서 5로 변경 | low | 없음 |
3. 첫 테스트 실패(`exit=2`)는 **내 실행 스크립트의 버그**였다(`python script.py` 는 현재 폴더를 모듈 경로에 넣지 않아 `src` 를 못 찾음). DevOrch 나 저장소의 문제가 아니었다. 고친 뒤 통과.

### 발견 (사용자의 저장소 쪽)
- 루트에 **빈 파일 `=0.40.0` 이 커밋돼 있다**(`pip install anthropic>=0.40.0` 을 따옴표 없이 실행해 생긴 흔적으로 보임). 이번 시험의 첫 작업으로 지웠고, 이 삭제는 복제본에만 있다(원격 미반영).

### 이 시험으로 말할 수 없는 것
- **비용:** mock 이라 $0 — 실제 리뷰어 비용·절감은 **측정하지 않았다**(`DOGFOOD_PLAN.md` 의 비용 측정은 아직 시작 전).
- **에이전트 동작:** 실제 에이전트(Claude Code)가 이 저장소에서 어떻게 일하는지는 보지 않았다.
- 분류 정확도: 내가 쓴 7개 문장으로 본 것이라 일반화할 수 없다.

### 다음
- 실제 리뷰어 비용을 재려면 API 키(환경변수)와 `config.yaml` 단가, `limits.max_cost_usd` 설정이 필요하고 **비용이 든다 → 사용자 동의 필요.**
- 발견 1·2 를 어떻게 할지는 사용자 결정(`project.test_env` 를 만들지, 분류 사례를 더 모을지).

## 시험 2 — 실제 에이전트(Claude Code)로 algo-pipeline 4건 (2026-10-18)

**방식:** 임시 복제본(원격 push 차단), 실제 Claude Code 2.1.293 을 헤드리스(`claude -p`, DevOrch MCP 서버 연결, 셸 실행 금지, 작업당 예산 상한)로 4번 실행. 리뷰어는 **가짜(mock)** 라 API 비용 $0, 구독 사용량만 소모(양은 측정하지 않음). 에이전트가 낸 `committed` 뒤의 `finish`·merge 는 복제본이라 내가 실행. `devorch finish` 는 사람이 하는 단계라는 설계는 그대로이고 에이전트는 직접 실행하지 않았다.

| # | 작업 문장 | 분류 | 리뷰어 | 승인 | 바뀐 파일 | 테스트 |
|---|---|---|---|---|---|---|
| 1 | README 의 설치 방법 문단에서 어색한 표현을 정리해줘 | low | 없음 | 불필요 | README.md | 200 통과 |
| 2 | check_setup.py 의 출력 문구를 정리해줘 | low | 없음 | 불필요 | check_setup.py | 200 통과 |
| 3 | 인스타그램 액세스 토큰이 로그에 그대로 찍히지 않도록 마스킹해줘 | medium | review, security(필요) | 불필요 | src/agents/analytics.py + 테스트 | 201 통과 |
| 4 | 발행 전에 승인 큐 상태를 확인하는 가드에서 빠진 경우가 없는지 점검하고 보완해줘 | **low** | **없음** | **불필요** | **src/db.py, src/dashboard/app.py, src/telegram_bot.py** + 테스트 2 | 203 통과 |

병합 뒤 복제본의 전체 테스트 203개 통과, 감사 로그 25건 서명 사슬 이상 없음.

### 된 것
- 에이전트가 4건 모두 `CLAUDE.md` 규칙대로(분석→수정→리뷰→테스트→적용) 진행했고 **`how_to_finish`·`merge_command` 를 그대로 전달**했으며 직접 실행하지 않았다(새 서버 코드에서 확인).
- `project.test_env` 로 이 저장소 테스트가 매번 DevOrch 안에서 통과했다.

### 발견
1. **작업 4 — 의심 사례 확인(판정은 사용자):** 발행 큐의 *상태 변경* 가드(DB 조건부 UPDATE, 대시보드 건너뛰기 라우트, 텔레그램 `/skip`)를 고치는 변경이 **LOW·리뷰어 없음·승인 없음**으로 커밋됐다. diff 기반 재평가(raise-only)도 **작동하지 않았다**(감사 로그에 `diff_reassessed` 없음). 이유: 작업 문장에 위험 신호가 없고, 재평가는 설계상 **파일 경로만** 보는데 `src/db.py` 는 힌트(`"/db/"`, `repository`, `migration` …)에 걸리지 않는다. 코드에 이미 적혀 있던 한계("무난한 이름의 파일 안의 위험한 편집은 알아채지 못한다")가 실제 저장소에서 관찰된 것이다. **그 변경이 올바른지는 나도 판단하지 못했고, mock 이라 어떤 리뷰어도 보지 않았다.** 규칙은 이 결과에 맞춰 고치지 않았다.
2. 작업 3은 문장의 `토큰` 때문에 medium(리뷰어 2개 필요)이 됐다. 바뀐 파일 경로(`src/agents/analytics.py`)에는 힌트가 없어서, **문장 없이 경로만 보면 올리지 못했을 것**이다(작업 문장이 사실상 위험도를 결정했다).
3. 한글로만 쓴 작업 문장은 브랜치 이름 슬러그가 비어 `devorch/<id>-task` 가 된다(작업 1 은 영어 단어 `README` 덕에 `-readme`). 어떤 브랜치가 무슨 작업인지 이름만으로 알기 어렵다 — 사소한 불편.

### 사용자의 저장소 쪽
- `.claude/settings.local.json` 이 공개 저장소에 추적되고 있다(이름이 '로컬' 설정). 내용은 열어 보지 않았다. 의도한 것인지 확인해 볼 만하다.

### 이 시험으로 말할 수 없는 것
- 4건·1개 저장소·내가 쓴 문장이다. 분류 정확도나 일반적인 절감은 말할 수 없다.
- **비용:** mock 리뷰어라 $0. 실제 리뷰어 비용·절감은 여전히 **측정하지 않았다.** 에이전트(구독) 사용량도 측정하지 않았다.
- 작업 4가 승인 대상이었다면 어땠는지(승인 흐름)는 이번엔 확인하지 못했다.
