## 시험 1 — algo-pipeline (2026-10-17)

**대상:** 사용자의 저장소 `YunhuPark/algo-pipeline`(Python, 인스타그램 카드뉴스 자동 발행, 테스트 30파일). 선택 이유: 소유한 저장소, pytest 경로(DevOrch 에서 가장 검증된 경로), 인증·발행처럼 위험도가 갈릴 만한 코드가 있음, 테스트가 있어 기준선 확인 가능. 같은 조건으로 비교한 다른 후보는 golden-time(TS+npm — npm 경로는 실제 저장소로 검증된 적 없음), yt-growth-coach(비공개 TS), IMST-Mamba(torch 필요).
**방식:** 사용자의 작업 폴더가 아니라 **임시 폴더에 새로 복제**해서 진행(원격에는 아무것도 push 하지 않음). 이 시험은 **가짜 리뷰어(mock, 비용 $0)** 로 DevOrch 의 분류·테스트·커밋 흐름만 확인했다. 실제 에이전트가 아니라 내가 스크립트로 에이전트 역할을 했다(작업 1건, 사소한 변경).

### 된 것
- 기준선: 새 복제본에서 테스트 **200개 통과**(저장소 자체 CI 와 같은 환경: `ALGO_ENV=test`, 가짜 키, 임시 DB). 테스트가 `.db` 등 부작용 파일을 남기지 않음.
- 작업 "루트에 잘못 생성된 `=0.40.0` 파일 삭제": 분석(LOW, 리뷰어·승인 불필요) → 리뷰(READY) → DevOrch 의 임시 worktree 에서 테스트 **200개 통과** → 별도 브랜치 `devorch/494ac382-0-40-0` 에 커밋(`d562bf8`, 삭제 1건만, 메시지에 위험도·`Human-Approved: not required`) → `devorch finish` 로 작업 트리 정리 → `git merge` fast-forward 성공. 내용 줄이 없는 **빈 파일 삭제 diff 도 문제없이 처리**됨.
- 테스트가 실패하면(아래 발견 3) `apply_changes` 가 "통과한 테스트 없음"으로 **막혔다**(fail-closed 확인).

### 발견 (DevOrch 쪽 — 후보 개선, 아직 만들지 않음)
1. **테스트에 환경변수를 넘기는 공식 방법이 없다.** 이 저장소의 테스트는 `TAVILY_API_KEY` 에 값이 *아무거나* 있어야 시작하는데, DevOrch 는 이름에 key/token/secret 등이 든 환경변수를 테스트 실행에서 제거한다(안전 장치, 의도된 동작). 그래서 그대로는 **테스트가 시작도 못 한다.** 이번에는 저장소 밖에 실행 스크립트(`run_tests.py`)를 두어 CI 와 같은 가짜 값을 설정하는 방식으로 우회했다. 이런 저장소(테스트에 가짜 키 필요)는 흔할 것으로 **추정**한다. 후보: `project.test_env`(리터럴 가짜 값만, 실제 비밀처럼 보이는 값은 거부). **→ 2026-10-18 구현함**(`config.yaml` 의 `project.test_env`, 테스트 19개 + 보호 5종 변형 시험). 같은 저장소에서 우회 스크립트 없이 `test_env` + 평범한 `pytest` 명령만으로 DevOrch 가 테스트 200개를 통과시키고 커밋함(작업 `abf26397`). 일반성은 저장소 1개 근거라 **추정**.
2. **위험도 분류 의심 사례 1건(판정은 사용자):** "인스타그램 발행 로직에서 **승인 큐를 우회하는 버그** 수정" 이 **LOW**(리뷰어·승인 없음)로 나왔다. 자동 게시 시스템의 발행 승인 우회라면 더 높아야 한다고 볼 수 있다. 단 이 분류는 diff 가 생기기 전의 작업 *문장* 기준이고, diff 가 생긴 뒤에는 실제 변경으로 위험도를 올리는 재평가(raise-only)가 있다 — 이 시험에서는 diff 를 만들지 않아 **재평가가 이것을 올렸을지는 확인하지 못했다.** 매처를 이 결과에 맞춰 고치지 않는다.
   | 작업 문장(내가 쓴 것) | 위험도 | 리뷰어 |
   |---|---|---|
   | 루트에 잘못 생성된 '=0.40.0' 파일 삭제 | low | 없음 |
   | README 오타 수정 | low | 없음 |
   | 인스타그램 발행 로직에서 승인 큐를 우회하는 버그 수정 | **low** | 없음 |
   | 인스타그램 액세스 토큰 갱신 로직 수정 | medium | review, security |
   | 카드뉴스 폰트 크기 조정 | low | 없음 |
   | 매일 실행 스케줄러 시간을 오전 9시에서 8시로 변경 | low | 없음 |
   | run_daily.py 의 재시도 횟수를 3에서 5로 변경 | low | 없음 |
3. 첫 테스트 실패(`exit=2`)는 **내 실행 스크립트의 버그**였다(`python script.py` 는 현재 폴더를 모듈 경로에 넣지 않아 `src` 를 못 찾음). DevOrch 나 저장소의 문제가 아니었다. 고친 뒤 통과.

### 발견 (사용자의 저장소 쪽)
- 루트에 **빈 파일 `=0.40.0` 이 커밋돼 있다**(`pip install anthropic>=0.40.0` 을 따옴표 없이 실행해 생긴 흔적으로 보임). 이번 시험의 첫 작업으로 지웠고, 이 삭제는 복제본에만 있다(원격 미반영).

### 후속 — `protected_paths` 구현과 재현 (2026-10-18)
시험 2 의 작업 4 에 대해 사용자가 "독립 확인이 필요하다"고 판단 → 키워드/경로 힌트를 이 사례에 맞춰 고치는 대신, **소유자가 직접 민감한 경로를 지정하는 정책**을 만들었다(`policy.yaml` 의 `protected_paths`, diff 가 그 경로를 바꾸면 위험도를 그 수준까지 올림 — 올리기만 함).
- 테스트 26개 + 변형 시험 7종(처음엔 1종 — '가장 높은 수준 대신 첫 항목' — 을 못 잡아서 내 테스트의 나열 순서를 고침, 이후 7종 모두 잡음).
- **같은 diff 로 재현:** 작업 4 의 커밋(`dcd1e1c`)과 *똑같은 diff* 를 그 부모 위에 적용하고 `src/db.py`, `src/dashboard/`, `telegram_bot.py` 를 high 로 지정 → 작업 문장 기준은 여전히 low 지만 diff 기준으로 **HIGH**, security+architecture 리뷰어 배정, 사람 승인 필요, `apply_changes` 는 `approval_required` 에서 멈춤. 이유가 어느 파일이 어느 패턴에 걸렸는지까지 기록됨.
- **이 결과가 보여 주는 것/아닌 것:** 소유자가 지정한 경로에 대해서는 게이트가 걸린다. 지정하지 않은 파일의 위험한 편집, 그리고 *무엇을 지정해야 하는지 소유자가 아는 것*은 여전히 사람 몫이다(경로만 보는 한계는 그대로). 근거가 사례 1건이라 "이 방식이 충분하다"고는 말하지 않는다. 리뷰어는 mock 이라 리뷰 품질은 이번에도 보지 않았다.

### 후속 — algo-pipeline 의 보호 경로 후보 (2026-10-20, 제안일 뿐 적용 안 함)
**방법:** 임시 복제본을 *읽기만* 해서 발행·큐 상태·인증·무인 실행·사람 승인·자동 답글 관련 파일을 찾음. 처음엔 소스 파일을 신호(발행 API, 토큰, DB 쓰기, 승인/큐, 스케줄) 개수로 순위를 매기고, 상위 파일의 설명·함수 목록을 읽어 역할을 확인했다. `comment_manager.py`, `dm_manager.py` 는 **신호만 확인했고 내용은 다 읽지 않았다**(그 파일이 사용자에게 자동 발송한다는 것은 이름·신호 기준의 추정). 목록: `docs/examples/algo-pipeline-protected-paths.yaml`(23개, high/critical 은 되돌릴 수 없는 외부 게시·큐 상태·인증·무인 실행 스위치, medium 은 대시보드·CI·가드 테스트처럼 "리뷰어는 붙고 사람 승인은 없음").
**검증:** `devorch doctor` 가 23개 패턴이 모두 추적 파일과 일치함을 확인.
**얼마나 자주 걸리나(사용성):** 이 저장소의 최근 60개 커밋(머지 제외)에 적용하면 지정 없음 46% / medium 이상 23% / high 이상 28% / critical 1%. 즉 **네 변경 중 하나쯤은 사람 승인이 필요해진다.** 이 이력은 DevOrch 작업이 아니라 이 저장소의 실제 커밋이라 DevOrch 로 일했을 때의 비율은 아니다. 가장 자주 걸린 패턴은 `tests/test_*guard*.py`(17), `content_queue.py`(7), `db.py`(6).
**거짓 양성(경로만 보는 한계):** `style: satisfy full pull request diff checks`(스타일 수정)가 `content_queue.py` 를 건드려 high 가 된다. 경로로는 스타일 수정과 로직 수정을 구별하지 못한다. 반대로 지정하지 않은 파일의 위험한 편집은 계속 놓친다.
**적용은 사용자 결정:** 원본 저장소에는 `.devorch/` 가 없다(복제본의 것은 내가 만든 로컬 설정). 적용하려면 `devorch init` 후 위 목록을 `policy.yaml` 에 넣고 커밋해야 한다.

### 열린 문제 — 정책·설정 파일은 보호되지 않는다 (코드 읽기로 확인, **재현은 안 함**)
`.devorch/**` 는 diff 수집에서 제외되고(`GitManager.DIFF_EXCLUDES`), `policy.yaml`/`config.yaml` 에 대한 무결성 검사도 없다. 정책은 MCP 서버가 시작될 때 읽는다. 따라서 파일을 쓸 수 있는 에이전트는 `.devorch/policy.yaml` 의 `protected_paths` 를 지우거나 `allowed_commands`/`config.yaml` 의 `test_command` 를 바꿀 수 있고, **그 변경은 어떤 리뷰된 diff 에도 나타나지 않으며** 서버가 다음에 시작할 때 적용될 것으로 추정된다. 보호 경로를 정해 놓아도 이 구멍이 있으면 의미가 줄어든다. 해결 방향(예: 정책 서명·해시 기록·시작 시 변경 경고)은 아직 설계하지 않았다.
